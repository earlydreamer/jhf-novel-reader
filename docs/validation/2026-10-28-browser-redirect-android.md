# 원문 브라우저 리디렉션 Android 검증

2026-10-28에 Black Shark 2의 기존 앱을 데이터를 유지하는 업데이트로 설치했습니다. 원문 브라우저에서 메인 프레임 리디렉션이 최종 주소로 열리는지와 기존 탐색 동작을 확인했습니다. Refs #392.

## 원인 확인

커밋하지 않은 진단 로그(`android.util.Log.d`)를 넣은 빌드로 수정 전 동작을 기록했습니다.

- pixiv 소설 홈에서 검색하면 `/search?q=Fantasy&…` 요청에 loader가 최종 주소 `/tags/Fantasy/novels`를 돌려줬습니다. 이때 `view.post` 안의 `view.getUrl()`은 아직 이전 주소(`/novel#discover`)였습니다. 그래서 다시 열기를 건너뛰었고, 그 뒤 차단 페이지가 `/search?…` 주소로 커밋됐습니다. 이 이동은 `hasGesture=true`인 페이지 쪽 이동이었습니다.
- 차단 화면에서 '뒤로 가기'를 누르면 WebView가 프래그먼트가 붙은 `/novel#discover`를 요청했습니다. loader는 프래그먼트를 뺀 `/novel`을 최종 주소로 돌려줬고, 두 문자열이 달라 리디렉션으로 판정됐습니다. 이번에도 `getUrl()`이 `/search?…`라서 다시 열기를 건너뛰고 차단 화면이 남았습니다. #392 본문의 "뒤로 간 소설 홈도 차단 화면" 현상의 원인입니다.

## 수정 후 실제 앱에서 확인한 흐름

주소와 `history.length`는 디버그 빌드의 WebView 원격 디버깅으로 읽었습니다. 나로우·카쿠요무는 사이트 안에 리디렉션되는 링크를 찾지 못했습니다. 그래서 같은 경로(페이지 스크립트가 시작한 이동)를 원격 디버깅의 `location.assign`으로 재현했습니다.

| 단계 | 관찰 결과 |
| --- | --- |
| pixiv 검색 | 소설 홈의 검색 아이콘을 탭하고 `fantasy`를 입력한 뒤 Enter를 눌렀습니다. 태그 목록(`/tags/Fantasy/novels`)이 열렸고 작품 목록이 보였습니다. |
| pixiv 뒤로 가기 | '뒤로 가기'를 탭하자 차단 화면 없이 `/novel#discover`가 열렸습니다. `history.length`는 2였고, 기록에 `/search?…` 항목이 남지 않았습니다. |
| pixiv 검색 결과 → 작품 | 다시 검색한 뒤 목록의 첫 작품을 탭했습니다. `novel/show.php?id=…`가 열렸고 '이 작품 열기'가 켜졌습니다. 서재에 추가하지는 않았습니다. |
| 나로우 301 | 나로우 홈에서 `https://yomou.syosetu.com/rank/genretop`(301 → `/rank/top/`)으로 이동했습니다. `/rank/top/` 랭킹이 열렸고 `history.length`는 2였습니다. '뒤로 가기'를 탭하자 차단 화면 없이 나로우 홈으로 돌아갔습니다. |
| 나로우 '이 작품 열기' | 서재에 있는 작품의 페이지(`ncode.syosetu.com/n9669bk/`)에서 '이 작품 열기'가 켜졌습니다. 누르자 서재의 기존 작품 화면이 열렸습니다. |
| 카쿠요무 307 | 카쿠요무 홈에서 `/rankings/all/daily`(307 → `?work_variation=long`)로 이동했습니다. 쿼리가 붙은 최종 주소의 랭킹이 열렸고, 작품 링크가 532개 있었습니다. |
| 카쿠요무 작품 → 뒤로 가기 | 랭킹의 첫 작품을 탭하자 '이 작품 열기'와 '뒤로 가기'가 켜졌습니다. '뒤로 가기'를 두 번 누르자 랭킹, 카쿠요무 홈 순서로 돌아갔고 차단 화면은 없었습니다. 서재에 추가하지는 않았습니다. |

원격 디버깅으로 사용자 활성화 없이 이동하면 '뒤로 가기'가 꺼졌습니다(`history.length` 2). 같은 이동을 사용자 활성화와 함께 실행하자 '뒤로 가기'가 켜졌습니다. Chromium은 사용자 활성화 없이 추가된 기록 앞의 항목을 뒤로 가기에서 건너뜁니다. 그래서 이 차이는 시험 방법에서 생긴 것으로 판단했습니다. 위 표의 나로우·카쿠요무 결과는 사용자 활성화를 준 이동입니다.
