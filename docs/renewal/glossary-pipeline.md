# 용어집 기반 번역 품질 파이프라인 설계 (초안)

상태: Claude Code·opencode 교차 정렬과 사용자 결정 반영. 2026-10-08 인계를 받아 E4B 입력 예산, 범위 스캔·후보 확정·배치 연결과 결정론 확인 표시까지 구현했다. 기본 모델은 E4B이며 Index 재평가는 선택 후속이다. 의미·말투 품질은 사용자 직접 테스트로 판단한다.
관련: #80(설계·교차검토), #81(파이프라인 구현), #72(의미 충실도), #75(일괄 번역), #21(작품 용어집).

## 1. 목표 (사용자, 2026-10-07)

1. 나로우계 소설 공통 **범용 용어집**을 확보해 디폴트로 적용한다.
2. 작품을 스캔해 **고유명사(인명 등) 추가 용어**를 확보한다.
3. 용어집 기반으로 품질을 확보한 번역을 한다.
4. Hy-MT2는 8K 컨텍스트·형식 문제로 기본 모델에서 내리는 방향을 검토한다. 온디바이스는 후순위다.

## 3. 합의된 방향

### 3.1 모델
- **Hy-MT2는 품질 목표에서 제외한다(사용자 확정).** 기존 8K 상한 가드는 남겨서 선택했을 때 깨지지 않게만 하고, 전용 프롬프트·형식에는 더 투자하지 않는다.
- 기본 모델 후보는 둘이다. 같은 회차·같은 용어집으로 A/B 실측해서 정한다.
  - **Gemma 4 E4B**: 범용 지시 모델이다. 앱 G1에서 누락 없이 통과했고 규칙 문장을 따른다. 지금 앱의 범용 라인 형식이 기준이다.
  - **Index-Translate-9B**: Hy-MT2 대안으로 제안받은 번역 특화 모델이다(Qwen3.5 기반, Apache-2.0, GGUF Q4_K_M 약 5.8GB). [모델 카드](https://huggingface.co/IndexTeam/Index-Translate-9B)상 확인한 점은 다음과 같다.
    - 학습 정렬 프롬프트가 **중국어**다. 용어집은 "硬性要求 专名/术语对照: 원문→번역、…" 형식의 **하드 제약**이고, 원문(【源文】)이 제약(【约束要求】)보다 앞에 온다. 말투·문체는 【注意】 연성 제약 자리에 들어간다.
    - **사고 모드를 꺼야 한다**(`chat_template_kwargs.enable_thinking=false`). 서버가 이 인자를 지원하지 않으면 `<think>` 블록 제거가 필요하다.
    - 벤치 평가는 16K 컨텍스트, 서빙 예시는 32K, 위치 임베딩은 262K다.
  - Index-Translate를 채택하면 **모델별 프롬프트 프로필**(범용 라인 형식 / Index 제약 형식)이 필요하다. 프로필 분기는 A/B 결과가 나온 뒤 채택 모델에 대해서만 구현한다.
- 형제 모델 **Index-NativeLong(Nailong)**은 문서 전체 단일 생성용이지만, 공식 템플릿이 zh↔en·zh↔ja뿐이고 벤치도 중국어 웹소설이라 **ja→ko 검증 경로가 없어 제외**한다.

### 3.2 주입 (#81에서 구현됨)
- 구간별 matched-only를 적용한다. 긴 이름부터 매칭하고 그 구간을 가린다. 용어와 말투는 이름공간을 나눈다.
- 형식은 `Reference the following translations:` + `원문 translates to 번역 (메모)` 라인을 지시문 앞에 두는 방식이다. 모델과 무관한 영어 라인 형식이라 범용 모델에도 그대로 쓴다.
- 완성본 provenance는 **회차에 적용된 항목의 해시**로 기록한다. 그 회차에 등장하지 않는 항목을 바꿔도 재번역 대상이 되지 않는다.
- 조용한 누락은 없다. 예산을 넘으면 첫 요청 전에 `input_limit`으로 실패한다.

### 3.3 예산
- 반복 실측에서 구간 크기는 품질 차이를 만들지 않았다. 그래서 예산 확대의 목적은 품질이 아니라 **용어집 주입 여유와 요청 수 감소**다.
- 전체 회차 평균 4.52B/토큰을 모든 문자열에 나누면 숫자·짧은 ID·희귀 문자가 과소 추정된다. 검증된 **Gemma 4 E4B**에만 문자별 여유를 둔다: 가나·한글 1, 기본 한자 2, 나머지는 UTF-8 바이트 수. 템플릿 여유 128도 유지한다. 다른 모델은 기존 1B/토큰 추정이다.
- 용량이 보고된 범용 모델은 컨텍스트에서 512를 뺀 뒤 입력에 약 1/3, 출력에 약 2/3를 예약한다. 입력/출력 상한은 32768/65536이다. 미확인 용량과 Hy-MT2 8K 가드는 기존 프로필을 유지한다. E4B 16K는 입력 5290 / 출력 10582다.
- 실제 E4B 토크나이저와 chat template를 적용한 13개 표본(대표 회차 3묶음, 합성 10개)은 모두 추정치 안이었다. 같은 103문단은 기존 계획 19묶음 → 새 계획 3묶음이다. 정확한 토큰 상한이나 모든 문자열에 대한 보장은 아니며, 서버의 한도 오류는 재전송 없이 표시한다. 상세와 원문 없는 지표는 [추정기 보정 기록](token-estimate-2026-10-08.md)을 따른다.

### 3.4 범용 용어집
- 대형 사전을 번들하지 않는다. 일반 어휘(`魔法→마법`)는 모델이 이미 맞게 번역하므로 예산만 쓴다. 범용 용어집은 **모델이 실제로 틀리는 장르 관례**를 겨냥한 작은 프리셋(수백 개 이내)으로 한다.
- **실측 필터**: 후보마다 "프리셋 없이 모델이 실제로 틀리는가"를 합성 예문으로 확인하고, 틀리는 항목만 넣는다. 다음 항목은 제외한다: 모델이 원래 맞히는 일반 외래어(`スキル`), 원문 문자열로 매칭되지 않는 문법 패턴(`～ぶり`)·개념(`呼び捨て`), 활용형이 매칭되지 않는 관용구(`油を売る`→`油を売って`), 작가가 의도적으로 '오용' 의미로 쓸 수 있는 어휘(`役不足`). 상대시간 같은 문형 오류는 용어집이 아니라 프롬프트 규칙으로 다룬다. 후보 출처는 [#80 R3](https://github.com/earlydreamer/narou-reader/issues/80#issuecomment-6039521664)다.
- 프리셋은 우리가 직접 작성해 번들한다. 공개 자료는 "어떤 개념이 반복되는가"를 보는 참고로만 쓰고, 한국어 표기는 생성 후 사람이 검수한다. 번들에는 CC0/MIT와 자체 작성분만 넣는다. KC3Kai는 칸코레 도메인이라 나로우와 관련성이 낮아 제외한다.
- 호칭 접미(`さん`, `ちゃん`)는 원문 문자열 치환이 아니라 주입 힌트로만 쓴다. `たくさん`·`みなさん`이 깨지기 때문이다.
- 계층은 범용 프리셋(읽기 전용) → 작품 용어집 → 말투다. 작품 항목이 같은 원문의 프리셋을 덮어쓴다.

### 3.5 작품 스캔
- 화 단위 블로킹 게이트는 쓰지 않는다. 일괄 번역을 끊기 때문이다.
- **배치 시작 시 범위 일괄 스캔 → 1회 확정 → 진행**으로 한다. 진행 중 새 후보는 플래그만 남기고, 배치가 끝난 뒤 사용자가 명시적으로 재번역한다.
- 추출은 규칙(루비 쌍, 카타카나 연속, 「」 화자 패턴)을 우선한다. LLM 추출은 선택 사항인 시드 스캔에만 쓴다.
- `origin: auto`(미확정) 항목은 주입과 적용 해시에서 모두 뺀다.
- 결정론 QA(잔존 일문, 확정 용어 미반영)는 **표시만** 한다. 자동 재번역은 승인 기획 14행 계약 위반이다.

## 4. 사용자 결정 (2026-10-07)

1. **Hy-MT2 제외 확정.**
2. **범용 용어집은 자체 작성 소형 관례 프리셋**(생성 + 검수)으로 한다.
3. **스키마 변경**: 별도 답은 없었다. 사용자가 앞서 저장 한도의 필요성 자체를 물었고, 작품 스캔에 `origin`이 필요해서 승인된 것으로 보고 진행했다. #78이 미릴리스라 `schemaVersion`은 그대로 두고 옵션 필드로만 추가했다(`850bda3`).
4. **나로우 이용규약 제14조 23호**("なろうデベロッパー API 이외의 자동 접근·데이터 수집 금지"): **개인 사용 한정, 이용자 개인 책임** 방향이다. 사용자 의견은 이렇다. "범위가 너무 넓어 해석에 따라 다르다. 관대하게 보면 사용자 기기·브라우저 위에서 동작하면 괜찮을 수도 있다. 기존 OSS 정책을 포함해 충분히 확인할 영역이다." → R1 조사 결과를 받아 원문 요청 사이 **최소 1초 간격**을 적용했다(`3eb99cb`, narou.rb 0.7초·WebToEpub 0.5초보다 보수적). 고지 문구·일괄 범위 상한은 추후 정한다. 운영사 지침상 본문·목차 파싱 표시는 명시적 위반 예시라서, 이 방향은 사용자 책임으로 남는다.

## 4.1 추가 결정 (2026-10-07) — 줄 ID·이어 보내기·미리보기

[colomo 번역기](https://syosetu.colomo.dev/)의 공개 번들을 분석한 결과다. 원문 각 줄을 `<p id="A">…</p>`처럼 짧은 ID로 감싸 보내고, 출력의 ID로 원문 줄에 대응시킨다. 그래서 줄 단위 표시, 잘린 지점 다음부터 이어가기, 묶음 크기 조정이 가능하다. 사용자가 이 방향의 두 가지를 허용했다.

1. **잘린 줄의 이어 보내기 허용**(횟수 상한 포함). 출력 한도가 실패 사유가 아니라 묶음 경계가 되므로, 출력 여유분을 크게 떼어둘 필요가 줄고 원문 길이와 상관없이 컨텍스트에 맞춰 묶을 수 있다.
2. **저장 전 미리보기 허용.** 저장·이어 읽기 기준은 완성본으로 유지한다.

설계 원칙:
- 줄 ID 대응은 스트리밍 없이도 동작한다(잘린 응답에서 완료 ID까지 취함). 앱의 CapacitorHttp는 스트리밍 응답을 받지 못하므로 먼저 비스트리밍으로 구현하고, 미리보기는 완료된 묶음 단위로 시작한다. 진짜 스트리밍은 네이티브 SSE 플러그인이 필요한 별도 과제다.
- 빠진 ID는 곧 빠진 문단이므로 **누락을 결정적으로 검출**한다(#48 유형). 검출 결과는 표시하고, 재요청은 사용자의 명시 동작으로 한다.
- 품질 수단은 용어집(일관성), 모델 선택(관용·의미), **앞 묶음 번역문 일부를 문맥으로 주입**(흐름·주어 생략)의 조합으로 보고 각각 실측한다.
- 따르지 않는 것: 검열 우회 재시도, 다중 키·프로젝트 순환, 프록시 경합 취득.
- 선행 조건: 소형 로컬 모델(E4B·Index-Translate)이 ID를 빠뜨리거나 합치거나 순서를 바꾸지 않는지 실측한다.

### 범위 스캔과 확인 표시의 구현 경계

- 새 배치는 범위 확인 → 후보 스캔 → 후보 확정 → 번역 시작의 명시 동작을 거친다. 스캔·확정은 생성 요청을 보내지 않는다. 범위의 루비와 두 번 이상 반복되는 카타카나를 모으고, 기존 확정 항목·프리셋은 제외한다. LLM 추출과 화자 패턴 추출은 이번 구현에 포함하지 않는다.
- 실패·중단된 스캔의 부분 결과는 확정할 수 없다. 완료된 후보와 확인 상태는 비공개 저널에 저장한다. 선택하지 않은 후보는 작품 용어집에 넣지 않는다. 확정 시 기존 수동 표기는 보존하고 배치의 용어집과 기존 완성본 재사용 개수를 갱신한다. 번역 진행 중에는 후보 확인 창을 띄우지 않는다.
- 원문 전문은 처음 8화까지만 메모리에 두어 곧 이어 번역할 때 재사용한다. 그 뒤 회차와 앱 재시작 후에는 번역 직전에 다시 가져온다. 범위 전체를 스캔하는 요청에도 기존 원문 요청 최소 1초 정책을 적용한다.
- 확인 규칙은 가나를 포함한 문단과, 원문에 적용된 용어의 확정 표기가 번역 전체에 한 번도 없는 경우를 표시한다. 주입과 같은 별칭·긴 이름 우선·작품 오버라이드 규칙을 사용하고 미확정 `auto`는 제외한다. 한자만 남은 일본어, 일부 등장분의 다른 표기, 의미·말투의 정성 품질은 판정하지 않는다. 이전 저장본은 계속 읽고 가나만 확인한다.
- 사용자 테스트 절차는 [휴먼 테스트 안내](human-test-glossary-2026-10-08.md)를 따른다. 기능 검증과 #72 품질 합격은 구분한다.
