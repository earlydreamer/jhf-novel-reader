# E4B 입력 추정과 컨텍스트 비례 예산

Claude의 2026-10-08 용어집·줄 ID 핸드오프(#80, Draft PR #81)를 이어받았다. `61f8715`의 716개 테스트·타입·린트·빌드와 두 GitHub CI는 통과한 상태였다. Windows CRLF 때문에 실패하던 포맷 검사는 작업 공간의 줄바꿈만 LF로 정규화해 해결했으며 그 과정에서 Git 내용 변경은 없었다.

기존 `estimatedLineTokens`는 UTF-8 바이트마다 1토큰을 잡고, 큰 컨텍스트에서도 입력 예산을 2048로 고정했다. 실제 E4B 일본어 입력은 평균 약 4.52B/토큰이지만 이 평균을 숫자와 희귀 문자에도 일괄 적용하면 과소 추정된다. 새 추정기는 확인한 `gemma-4-E4B` 식별자에만 가나/한글 1, 기본 한자 2, 나머지는 바이트 수를 적용하고 128토큰의 템플릿 여유를 유지한다. 다른 모델과 이전 호출자는 바이트 추정을 유지한다.

서버에서 컨텍스트가 보고된 범용 모델은 512토큰을 남긴 뒤 입력에 약 1/3, 출력에 약 2/3를 배분한다. 각각의 상한은 32768/65536이다. 보고되지 않은 용량과 Hy-MT2 8K 제한은 기존 프로필이다. E4B 서버의 실제 16384컨텍스트에서는 입력 5290, 출력 10582를 사용한다. 완료본에는 `estimator`를 선택 메타데이터로 남긴다. 해당 필드가 없는 이전 `lines-v1`/`segments-v1` 저장본도 읽히며, 모르는 추정기 이름은 저장 검증에서 거부한다.

## 실제 토크나이저 확인

서버는 기존 Linux E4B/llama.cpp b11146를 그대로 사용했다. [해당 버전의 공식 API 문서](https://github.com/ggml-org/llama.cpp/blob/7fe450e19305b828c199d602c23a8337aaa1f03b/tools/server/README.md#post-apply-template-apply-chat-template-to-a-conversation)에 따른 `/apply-template` → `/tokenize`를 호출했다. 이 검사는 추론을 실행하지 않았고 생성 POST는 0회다.

같은 대표 회차의 비공백 103문단을 새 추정기로 계획하면 **19 → 3묶음**이다. 원문은 이전 비공개 실기 증거의 스냅샷이며 다시 사이트에서 수집하지 않았다.

숫자, 영문 혼합 문자열, 희귀 한자·보충 문자·이모지, 줄 ID, 한국어와 용어집을 포함한 합성 10개도 실제 토큰 수가 추정치 안이었다. [원문 없는 토큰 지표](evidence/token-estimate-2026-10-08/calibration.json)에 기록했다. 이 표본 검증은 정확한 tokenizer 구현이나 모든 입력에 대한 수학적 상한을 뜻하지 않는다. 서버 입력 한도 오류의 기존 분류·자동 재전송 금지는 유지한다.

## 기기 검증의 구분

Black Shark 2(API29)는 ADB에서 사용 가능하다. 기존 앱과 현재 PC의 debug signer가 달라 생산 패키지 `install -r`는 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`로 거부됐다. 기존 앱을 제거하거나 데이터를 초기화하지 않았다. 기존 10파일·설정·설치 APK를 비공개 작업 폴더에 백업했다.

검증에는 소스 수정 없이 작업 소유 Gradle init script가 applicationId만 `app.narou.reader.proof80`으로 바꾼 별도 debug 패키지를 사용한다. 정상 생산 APK의 출처·서명·보안·웹 자산 감사와 이 테스트 패키지의 실기 실행은 구분한다. 기존 앱의 덮어쓰기나 생산 패키지에서의 업그레이드 검증으로 보고하지 않는다.
