# #48 후속 조사 — 입력 길이 한계와 양자화 분리

2026-10-05 KST. 대상은 [#48](https://github.com/earlydreamer/narou-reader/issues/48)이다. 이전 조사([issue-48-investigation-2026-10-05.md](issue-48-investigation-2026-10-05.md))가 LM Studio와 독립 llama.cpp의 출력 동일성을 확인한 뒤, 이번에는 **다른 각도**(입력 길이·프롬프트 형식·입력 구조·양자화)에서 원인을 분리했다. 앱의 프롬프트·제공자·저장 형식·설정은 수정하지 않았다.

## 결론

**번역 누락과 조기 종료의 직접 원인은 Hy-MT2 7B 모델 자체의 장문 입력 처리 한계다. 입력이 약 5,500 prompt 토큰을 넘으면 생성이 붕괴한다.** 프롬프트 형식, 입력 구조(빈 문단), 양자화(Q4/Q8), 런타임(LM Studio/llama.cpp)은 모두 원인이 아니다.

## 실험 환경

- MAINPC LM Studio, 로드 인스턴스 `narou-hy-mt2-7b`(Hy-MT2-7B-Q4_K_M, 4.62GB) 및 `hy-mt2-7b-q8`(Hy-MT2-7B-Q8_0, 7.98GB).
- context 16,384, parallel 4, flash attention on, offload KV to GPU on.
- 진단 모드 `no-repeat`(단일 user 메시지, `temperature=0`, `repeat_penalty=1.0`)를 기본으로 사용. 프롬프트·앱 조건 비교에서 `official`(단일 user)과 `app`(system+user, 서버 기본 샘플링)을 별도 실행.
- 소스는 승인된 `https://ncode.syosetu.com/n6517bw/3/`. 정규 입력 7,258자, 비공백 문단 103개, SHA-256 `728939898a852f0c93764a984fe043c5f73ea73010fd4bc5af66a418419d2132`. 도구는 원본 소스 해시가 다르면 생성하지 않는다.
- 진단 도구 `tools/diagnostics/hymt2-fidelity.mjs`에 `--scope nonempty-<start>-<end>`, `--drop-blank`, `--collapse-blank`를 추가했다. 본문·raw 응답은 저장하지 않고 해시·토큰·단서 개수만 기록한다.

## 입력 길이 스윕 (Q4_K_M, no-repeat)

| 범위(비공백) | inputChars | prompt tokens | completion tokens | total | output chars | blocks | 결과 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1–52 | 3,806 | 3,398 | 4,088 | 7,486 | 4,285 | 52 | 완전 번역, 단서 보존 |
| 1–77 | 5,500 | 4,890 | 5,914 | 10,804 | 5,989 | 77 | 완전 번역, 단서 보존 |
| 1–90 | 6,289 | 5,586 | 26 / 28 | 5,612 / 5,614 | 23 / 27 | 1 | 조기 EOS 붕괴 |
| 1–103(전체) | 7,258 | 6,422 | 5,712 | 12,134 | 5,724 | 71 | 28–32문단 누락 |
| 53–103 | 3,430 | 3,037 | 7,661 | 10,698 | 4,490 | 34 | 마력 단서 5/13 부분 누락 |

핵심: **입력이 4,890 토큰까지는 완전 번역, 5,586 토큰에서는 20여 자 생성 후 종료.** 총합 8K 초과가 직접 원인이 아니다(1–77은 총합 10,804로 8K를 넘었는데 정상).

## 대조군 — 모든 대안 가설 기각

- **프롬프트 형식**: 1–90을 `official`(단일 user)로 보내면 23자(hash `ce162f9a...`), `app`(system+user, 서버 기본)로 보내면 24자(hash `13f39a0d...`)로 동일하게 붕괴. `faithful`(전체 번역 강제)의 27자 응답(hash `e138b5c3...`)도 1–90 재실행에서 같은 해시로 재현되어, 이는 "지시 위반"이 아니라 입력 길이에 의한 붕괴였음이 확인됐다.
- **입력 구조**: 빈 문단 연속 개행 정리(`--collapse-blank`, inputChars 7,258→7,094)와 빈 문단 제거(`--drop-blank`, 7,076) 모두 output 블록 71/74로 근본 해결이 안 됨.
- **양자화**: Q8_0(7.98GB)으로 1–90은 23자(hash `af55f1b3...`)로 붕괴, 전체는 4,169자/53블록으로 오히려 더 짧게 누락. Q4와 동일한 실패 → 양자화 아님.
- **런타임**: 이전 조사에서 LM Studio와 독립 llama.cpp b11415가 같은 출력을 냈고, llama.cpp에 해당 known issue가 없다.

## 참고 — 로컬 번역 모델 교차 비교(무효)

`ja-ko-vn-12b-v2`(gemma3 12B, Q6_K)로 같은 입력을 보냈으나 전체 21토큰/38자, 앞 절반 39토큰/61자로 붕괴했다. 이는 이 모델이 진단 도구의 영어 instruction 형식과 맞지 않아(자체 프롬프트 템플릿 필요) 발생한 것으로, 번역 능력 비교로 성립하지 않는다. Hy-MT2만 프롬프트가 맞으므로 모델 간 비교는 이번 실험의 근거로 사용하지 않는다.

## 비결정성 관찰

`temperature=0`, `repeat_penalty=1.0`의 동일 조건에서 반복 실행 시 출력이 달라졌다(전체 실행 4,641자 vs 5,724자, 1–90 23자 vs 27자). 이전 조사의 "동일 SHA"는 특정 시점의 일치였고, CUDA/flash-attention 커널 비결정성과 긴 시퀀스 오차 증폭으로 보인다. 따라서 단일 실행의 해시 일치를 재현성의 증거로 쓰지 않는다.

## 의미와 한계

- 앱의 승인 계약(전체 회차를 **한 번의 생성 POST**로)은 Hy-MT2 7B의 실제 장문 처리 능력과 충돌한다. 전체 회차 입력(6,422 prompt 토큰)이 붕괴 임계(~5,500)를 넘는다.
- Tencent 공식 답변(HF `Hy-MT2-7B-GGUF` discussion #3: "max context 8K, 긴 텍스트에서 성능·지시 저하")과 GitHub README의 `max_context: 8192`에 부합한다.
- **미검증**: BF16(비양자화)과 llama.cpp 외 구현(Transformers 등)은 이번에 실행하지 않았다. 다만 Q4와 Q8이 동일하게 실패했으므로 양자화 영향은 작다고 본다.
- 단일 소스(한 회차), 비결정적 실행, 진단용 부분 범위라는 한계가 있다. 완전한 의미 대조는 수행하지 않았고 단서 개수와 블록 수로 판정했다.
- 임시 로드한 `hy-mt2-7b-q8`는 실험 후 정리 대상이며, 원래 로드돼 있던 Q4 인스턴스는 유지했다.

## 증거

`docs/renewal/evidence/issue-48-context-limit-2026-10-05/`의 14개 JSON(`expA`…`expG`). 본문·raw prompt/response·인증값은 포함하지 않는다.

## 다음 판별 실험

1. 같은 7B의 **BF16을 Transformers 등 llama.cpp와 다른 구현**에서 실행해 모델 자체와 공통 구현을 완전히 분리한다.
2. 완화 후보를 평가할 때는 one-shot 계약(숨은 청킹·자동 재시도 없음)을 유지해야 하며, 입력 길이를 임계 아래로 줄이는 방법(예: 화 분할)은 제품 계약 변경이므로 별도 승인이 필요하다.
3. 해결 후보는 전체 회차 처음부터 끝까지 의미 대조 후 실제 앱·기기 G1으로 검증한다. HTTP 200/stop과 단서 존재는 G1 PASS를 대체하지 않는다.
