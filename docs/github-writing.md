# GitHub 글 작성 기준

이슈·PR·댓글은 계정 소유자의 프로젝트 기록으로 작성합니다. 문제, 결정, 변경 결과와 확인 근거를 먼저 설명합니다. Codex·Claude·OpenCode 등 작성 도구가 달라도 이 기준을 사용합니다.

## 화자와 문체

- 본문은 주어를 생략한 한국어 평서체로 씁니다. 현재 동작·방침은 `~한다`, 완료한 작업은 `~했다`, 미확인 사항은 `~하지 않았다`로 구분합니다. 제목·표·체크리스트에는 짧은 명사형도 사용할 수 있습니다.
- `사용자 요청에 따라`, `사용자가 시켜서`, `요청하신 대로`, `구현해 드렸다`처럼 계정 소유자와 작성자를 분리하는 표현은 쓰지 않습니다. 필요한 요구와 결정 자체를 직접 적습니다.
- 제품 이용자를 뜻하는 `사용자`는 사용할 수 있습니다. 다른 사람의 실제 제보나 인용은 출처를 유지합니다. 개인 확인과 자동 검증, 직접 검토와 독립 리뷰를 구분하는 데 필요한 수행 주체도 남깁니다.
- 에이전트의 인사·칭찬·다짐·자기평가·고정 서명은 붙이지 않습니다. 작성 도구 표시가 필요한 경우 짧은 출처로 남깁니다. 기존 글의 도구·검토자 정보는 소급 정리 중 임의로 삭제하지 않습니다.
- 저장소의 사용·기여 안내는 기존 한국어 합니다체를 유지합니다. 이 기준의 평서체는 GitHub 이슈·PR·댓글에 적용합니다. 코드·명령·로그·UI 문구·직접 인용은 원문을 유지합니다.

| 정리 전 | 정리 후 |
| --- | --- |
| 사용자 요청에 따라 목차 페이징을 수정했습니다. | 최근 읽은 회차가 포함된 목차 페이지를 먼저 열도록 수정했다. |
| 요청하신 작업을 성공적으로 완료했습니다. | PR #123을 main에 병합했다. Checks와 Android CI가 통과했다. |
| 사용자가 main 병합을 원하지 않아 중단했습니다. | main 병합은 보류했다. 연구 결과는 `codex/research-example`에 보존했다. |
| 완벽하게 해결했고 안정성을 크게 개선했습니다. | 회귀 검사 12개가 통과했다. 실제 기기의 재현 여부는 확인하지 않았다. |

예시는 표현 방식의 비교입니다. 실제 글에서는 원문의 수치·이유·결정 시점·관련 링크·남은 조건을 함께 유지합니다. 근거가 없는 결과를 새로 만들지 않습니다.

## 정보와 구조

첫 문장에 핵심 문제나 결과를 적습니다. 각 문단은 한 가지 내용을 다루고, 여러 결과를 비교할 때 목록이나 표를 사용합니다. 긴 코드·로그에는 코드 블록을 사용하되 공개할 수 있는 내용인지 확인합니다.

제목은 [유지관리 규칙](maintaining.md)의 형식을 따릅니다. 본문은 아래 순서를 기본으로 하며 해당하지 않는 항목과 작성 안내 문구는 게시 전에 지웁니다. 짧은 변경은 같은 정보를 담은 한두 문단으로 작성할 수 있습니다. 상세 기기 검증에는 소제목을 추가합니다.

| 대상 | 기본 구성 |
| --- | --- |
| 기능·문서·관리 이슈 | 목적 → 범위 → 완료 조건 → 관련 작업 → 검증 계획 |
| 버그 이슈 | 현상과 재현 → 기대·실제 동작 → 확인 근거·원인 가설 → 수정 범위·완료 조건 → 관련 작업 |
| PR | 문제와 변경 결과 → 관련 이슈·변경 범위 → 검증 → 남은 조건 |

이슈 본문은 요구와 완료 조건의 기준입니다. PR 본문은 최종 변경을 처음 읽는 사람이 이해할 수 있도록 갱신합니다. 진행 경과와 상세 검증은 댓글에 기록하고 필요한 곳에서 링크합니다. 구현·테스트·실기·CI·병합은 각각 근거가 있을 때만 완료로 표시합니다.

검증에는 수행한 검사, 대상 소스와 환경, 결과 및 한계를 적습니다. 실패 후 재실행했다면 최초 실패와 재실행 조건을 남깁니다. 요약을 추가해도 원래의 상세 근거를 없애지 않습니다.

## 댓글

여러 문단의 작업 댓글은 첫 줄에 `### 진행`, `### 검증`, `### 검토`, `### 리뷰 반영`, `### 완료`, `### 정정` 중 목적에 맞는 제목을 붙입니다. 검토에서 발견한 사항과 실제 반영한 결과를 구분합니다. 보류·중단·대체 결정은 `### 결정`을 사용합니다. 필요하면 `### 검증: Android 설치와 데이터 보존`처럼 대상을 덧붙입니다. 기준 소스·기기·판단 시점은 본문에 남깁니다.

모든 댓글에 같은 빈 항목을 강제하지 않습니다. 단순 질문·짧은 답변·인라인 리뷰 답글은 바로 본문을 씁니다. 봇 명령과 자동 처리 표식은 형태를 유지합니다. 기존 댓글을 소급 정리할 때 의미 있는 제목·날짜는 보존하고 이에 대응하는 분류를 사용합니다.

### 진행 예시

```markdown
### 진행

작품 단위 일괄 조회를 Draft PR #123에 올렸다. 기존 저장본의 소유권·손상 검증은 유지했다.

- 검증: 관련 회귀 검사 12개 통과. CI는 실행 중이다.
- 남은 조건: Android에서 진입 시간과 설치 후 데이터 보존을 확인한다.
```

### 검증 예시

```markdown
### 검증: Android 진입 시간

Android 10에서 같은 작품의 목차 진입을 변경 전후 각 3회 측정했다. 대상 소스는 `abc1234`다.

| 대상 | 측정값 | 중앙값 |
| --- | --- | --- |
| 변경 전 | 900 / 1,200 / 1,100ms | 1,100ms |
| 변경 후 | 120 / 110 / 130ms | 120ms |

기존 작품·설정 해시는 설치 전후 일치했다. 실제 모델 통신과 iPhone 동작은 확인하지 않았다.
```

### 리뷰 반영·완료·정정 예시

```markdown
### 리뷰 반영

취소 전에 저장한 시도 기록이 자동 번역을 막는 지적을 반영했다. 미전송이 확인된 기록만 되돌린다.

- 반영 커밋: `abc1234`
- 검증: 전송 전 취소·결과 불명 요청의 회귀 검사 8개 통과.
- 남은 의견: 없음.
```

```markdown
### 완료

PR #123을 main에 병합했다. 병합 커밋은 `abc1234`이며 해당 head의 필수 CI가 통과했다.

실제 기기 검증은 수행하지 않았다. 기기 확인은 #124에서 이어간다.
```

```markdown
### 정정

앞선 댓글의 설정 보존 판정에는 설치 전 기준선이 없었다. 해당 결과를 설치 전후 보존의 근거로 사용할 수 없다.

추가 설치를 중단하고 현재 데이터를 보관했다. 유실 시점은 미확정이며 #124에서 복구와 원인을 확인한다.
```

완료 댓글은 결과·근거·남은 조건만 적고 본문 전체를 다시 붙이지 않습니다. 과거의 잘못된 결과를 정정할 때는 기존 주장을 조용히 덮어쓰지 말고, 무엇을 왜 정정하는지 연결된 기록을 남깁니다.

## 기존 글에 소급 적용

소급 적용의 목표는 정보 보존과 가독성 개선입니다. 짧게 만들기 위해 원문의 원인·선택 이유·대안·검증 수치·환경·실패·미검증·보류 조건·출처를 삭제하지 않습니다. 정보가 많으면 소제목·목록·표로 정리하고 요약 뒤에도 세부 근거를 남깁니다.

1. **대상을 확보합니다.** 열린 항목과 닫힌 항목을 구분해 이슈·PR 본문, 일반 댓글, 인라인 댓글과 리뷰 본문을 조회합니다. 작성 계정을 확인하고 봇·다른 계정의 글은 제외합니다. 원본 내용·제목·URL·ID·수정 시각을 저장소 밖에 보관합니다.
2. **변경안을 만듭니다.** 중계식 표현과 혼합 문장형을 고치고 정보를 주제별로 묶습니다. 코드·로그·인용·링크·체크박스·멘션·자동 처리 표식은 보존합니다. 기존 작성 도구 정보도 별도 출처로 유지합니다. 이미 읽기 좋은 글은 그대로 둡니다.
3. **의미와 시점을 대조합니다.** 커밋·해시·수치·단위·날짜·명령·관련 이슈·URL뿐 아니라 부정·조건·원인 가설·승인 주체·중단 이유가 유지되는지 diff를 읽습니다. 단순 토큰 일치만으로 의미 보존을 판정하지 않습니다. 과거 댓글의 `진행 중`을 현재의 `완료`로 바꾸거나 과거 검증을 재실행한 것처럼 쓰지 않습니다. 당시 요구·진행 상태에는 필요하면 `등록 시점`·`기록 시점`을 표시합니다.
4. **기존 글을 갱신합니다.** 게시 직전에 내용을 다시 읽고 원본과 달라졌다면 변경안을 재검토합니다. 본문만 수정하며 문체 정리를 이유로 상태·라벨·담당자·리뷰 판정·스레드 해결 상태를 바꾸지 않습니다. 같은 내용의 새 댓글을 일괄 추가하거나 과거 댓글을 삭제하지 않습니다.
5. **결과를 확인합니다.** API 응답 후 다시 조회해 변경안과 일치하는지 확인합니다. 수정·유지·제외·충돌/실패 수와 대표 URL을 관리 이슈에 기록합니다. 원본·변경안·적용 결과는 복구할 수 있도록 비공개 로컬 경로에 보관합니다. 공개 기록에는 비밀값이나 전체 백업을 첨부하지 않습니다.

문체 수정 중 사실 오류를 발견하면 같은 작업으로 조용히 바꾸지 않습니다. 정정 이유와 근거를 별도로 기록하고 새 검증이나 제품 변경이 필요하면 별도 작업으로 연결합니다. 대량 변경은 검토한 소규모 묶음으로 적용하고 API 제한·동시 수정·실패가 발생하면 해당 항목을 남겨 재개합니다.
