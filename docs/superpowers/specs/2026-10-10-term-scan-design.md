# 용어집 자동 생성과 용어 정밀스캔 설계

- 상태: 확정(2026-10-10, 사용자 결정 반영)

- 작성: 2026-10-10
- 관련: #72(로컬 모델 의미 충실도), #147(용어집 편집 보강)

> **2판 변경(2026-10-10, 사용자 결정):** 별도 검색 서버(SearXNG)나 외부 검색 업체 계정(Brave·Tavily 등)이 필요한 구조는 '앱 + 사용자의 로컬 LLM'이라는 앱 컨셉과 맞지 않아 범위에서 뺀다. 정밀스캔은 오프라인 규칙, 원문 안의 근거, 로컬 모델의 다단계 추론으로 하고, 키 없는 공개 사전 API(위키백과·위키데이터)만 선택 사항으로 둔다. 아래 §5·§6·§7·§9는 2판 기준이다. 일반 웹 검색 조사 결과는 §6 끝의 '범위에서 뺀 것'에 기록으로 남긴다.

## 1. 배경: 실험으로 확인한 것

Fold7(v0.1.13, gemma-4-E4B, llama.cpp)에서 한 회차(문단 263개)를 두 번 번역해 원문과 대조했다.

| 항목 | 용어집 없음 | 모델이 만든 용어집(22항목) 적용 |
|---|---|---|
| 같은 고유명사의 표기 흔들림 | 있음(지명 2가지 표기) | 없음(용어집 표기로 고정) |
| 실존 인물 읽기 | 틀림(도조) | 맞음(도산, 용어집에서) |
| 용어집 자체의 오류 | 해당 없음 | **그대로 퍼짐**(카밀라→카미라, 그레이런→그레이른, 아르카디아→알카디아) |
| 역사 별명(『美濃の蝮』 등) | 틀림 | 여전히 틀림(용어집도 틀림) |
| 일반 어휘·문장 의미 오류 | 약 4% 문단 | 비슷함(재번역마다 달라짐) |

- 생성 비용: 입력 약 4,500토큰, 출력 약 800토큰의 요청 1회. 번역 1회(77초)보다 훨씬 작지만, 번역 전에 기다리면 첫 문단이 그만큼 늦어진다.
- 지금 앱에는 자동 생성이 없다. 후보 스캔은 '미리 번역'에만 있고, 사용자가 한국어 표기를 직접 입력해야 적용된다. 기기의 용어집은 실제로 비어 있었다.

**결론**
- 용어집은 **일관성**을 확실히 준다.
- **정확성**은 용어집 품질만큼만 나온다.
- 모델이 원래 모르는 지식(역사 별명, 정식 한국어 표기)은 외부 근거로 보강해야 한다.

## 2. 목표와 비목표

**목표**
1. 번역 전에 용어집을 자동으로 만들어 바로 적용한다(옵션). 사람은 나중에 고친다.
2. 목차 화면의 컨텍스트 메뉴에서 '용어 정밀스캔'을 실행해, 원문 안의 근거와 로컬 모델의 다단계 추론으로 용어집을 개선한다. 별도 서버나 외부 계정 없이 앱과 사용자의 로컬 LLM만으로 동작한다.
3. 사람이 고친 항목은 기계가 덮어쓰지 않는다.

**비목표**
- 일반 어휘·문장 의미 오류의 해결. 이건 모델 독해력 문제로, 더 큰 모델을 쓰는 것 말고는 앱에서 근본 해결이 어렵다.
- 소설 본문을 외부 검색 서비스로 보내는 것.

## 3. 용어 데이터 모델

`GuidanceTerm.origin`을 다음처럼 나눈다. 현재는 `'auto'`(미확정 후보, 미적용)와 `undefined`(사람 확정)만 있다.

| origin | 의미 | 번역 적용 | 기계가 덮어쓰기 |
|---|---|---|---|
| `undefined` | 사람이 입력·수정 | 적용 | 안 함(제안만) |
| `'model'` (신규) | 빠른 자동 생성 | 적용 | 정밀스캔이 덮어씀 |
| `'scan'` (신규) | 정밀스캔이 근거와 함께 확정 | 적용 | 다음 정밀스캔이 더 강한 근거일 때만 |
| `'auto'` | 기존: 미리 번역 후보(미확정) | 미적용 | — |

- `'scan'` 항목에는 `evidence: { kind, url?, note }[]`를 단다. 용어집 화면은 이걸 근거 링크로 보여 준다.
- 사람이 `'model'`이나 `'scan'` 항목을 고치면 `origin`이 `undefined`로 바뀐다.
- 저장 형식이 바뀌므로 `src/translation/guidance.ts` 검증과 마이그레이션 테스트를 함께 고친다.

## 4. 기능 A: 빠른 자동 용어집 (설정 옵션)

- **설정:** 번역 방식 아래 '번역 전 용어집 자동 생성' 스위치. 기본값은 사용자가 정한다(§9).
- **언제 도는가:** 회차 번역을 시작하기 직전, 그 회차 원문에 **아직 용어집에 없는 후보가 있을 때만**. 작품의 첫 회차에서 주로 돌고, 이후 회차는 새 이름이 나올 때만 돈다.
- **절차**
  1. 규칙 후보: 기존 `scanNameCandidates`(루비, 반복 가타카나).
  2. 모델 요청 1회: 후보 목록과 그 회차 원문을 주고 JSON을 받는다. 프롬프트는 다음을 지시한다.
     - 고유명사·별명만 남기고 일반 외래어와 의성어는 뺀다.
     - 한자 고유명사와 별명을 추가로 찾는다.
     - 한국어 표기와 분류를 정한다.
     - 응답은 `response_format: json_schema`(llama.cpp·LM Studio 지원)로 받고, 실패하면 텍스트에서 JSON을 추출한다.
  3. (정밀스캔 단계로 이동) 가타카나 발음과 모델 표기가 크게 어긋나면 낮은 신뢰도로 표시만 한다. 일본어 표기법 변환은 판타지 이름의 원어(예: Camilla→카밀라)를 복원하지 못하므로 표기를 대신 정하지 않는다.
  4. 결과를 `origin: 'model'`로 저장하고 바로 적용해 번역을 시작한다.
- **실패 처리:** 생성이 실패하거나 시간을 넘기면(기본 30초) 용어집 없이 번역을 진행하고 상태 알림으로만 알린다. 번역을 막지 않는다.
- **비용:** 작품당 처음 한 번에 15초 안팎(추정). 이후에는 새 이름이 있을 때만 든다.

## 5. 기능 B: 용어 정밀스캔 (목차 컨텍스트 메뉴)

- **진입:** 작품 목차의 상단 메뉴에 '용어 정밀스캔'을 둔다. 회차 메뉴(⋮)에서 범위를 지정해 실행할 수도 있다.
- **입력:** 이미 받아 둔 원문 회차(저장본의 원문 스냅샷)와 현재 용어집. 추가로 원문을 받지는 않는다. 필요하면 범위를 먼저 받는다.
- **실행 모델:** 결정적 파이프라인을 기본으로 한다(§5.2).

### 5.1 단계

1. **수집:** 규칙 후보와 모델 추출(한자 고유명사, 별명, 호칭)을 모은다. 후보마다 출현 횟수와 짧은 문맥(앞뒤 40자)을 함께 둔다.
2. **분류(모델):** 각 후보를 셋 중 하나로 나눈다. 실존 고유명사(역사 인물, 실제 지명, 실제 작품) / 작품 고유 이름 / 일반어. 일반어는 버린다.
3. **근거 모으기(앱이 실행, 별도 서버 없음)**
   - **원문 안의 근거(Tier 0):** 작가가 단 루비(읽기), 여러 회차에서 같은 이름이 나온 문맥, 작품 소개·키워드. 작품 소개와 키워드는 앱이 이미 접속하는 소설 사이트에서 얻는다.
   - **작품 고유 이름(Tier 0):** 루비가 있으면 그 읽기를 가장 강한 근거로 쓴다. 표기는 모델이 정하고, 가타카나 발음과 크게 어긋나면 표기법 변환기 검사로 낮은 신뢰도를 표시한다(변환기가 표기를 대신 정하지 않는다).
   - **별명·호칭(모델 단계 분해):** 바로 표기를 정하지 않는다. 먼저 구성 글자·단어의 뜻을 뽑고(蝮→살무사), 문맥에서 무엇을 가리키는지 정한 뒤, 뜻으로 옮긴 표기를 조합한다(미노의 살무사).
   - **실존 인물·지명·역사 별명(Tier 1, 선택):** 위키데이터 한국어 라벨·가나 읽기, 위키백과 일→한 언어 링크와 넘겨주기 문서. 넘겨주기를 따라가면 별명이 실제 인물 문서로 이어진다(美濃の蝮→斎藤道三→사이토 도산).
   - **작품 고유 이름·캐릭터명·별명(Tier 1, 선택):** 나무위키를 일본어 원문으로 검색해 '한국어 표기 (日本語)' 패턴을 찾는다. 작품 제목으로 작품 문서와 등장인물 문서를 찾고, 그 안에서 후보 이름을 찾는다.
4. **판정(모델, 다수결):** 후보마다 모은 근거를 붙여 최종 표기, 신뢰도(높음/보통/낮음), 근거를 JSON으로 받는다.
   - 같은 판정을 3회 묻는다(온도를 약간 올림). 일치하면 '높음', 갈리면 다수 표기와 '보통/낮음'을 매긴다.
   - 근거 우선순위는 다음 순서로 프롬프트와 후처리에 넣는다.
     1. 작가가 단 루비(읽기)
     2. 나무위키의 '한국어 (日本語)' 표기, 한국어 위키·위키데이터 표기(Tier 1을 켰을 때)
     3. 표기법 변환
     4. 모델 추정
5. **적용과 보고**
   - `'model'`이나 근거가 약한 `'scan'` 항목은 새 결과로 바꾼다.
   - 사람이 고친 항목은 '제안'으로만 남긴다.
   - 결과 화면에 바뀐 항목, 근거 링크, 신뢰도를 보이고 항목별 되돌리기를 준다.
   - 신뢰도가 낮은 항목은 맨 위에 모아 사람이 볼 곳을 좁힌다.

### 5.2 도구 호출(모델이 조회를 정함) 대 결정적 파이프라인(앱이 조회를 정함)

- **도구 호출은 모델이 스스로 인터넷에 접속하는 기능이 아니다.** 모델은 "이 도구를 이 인자로 불러 달라"는 요청만 내고, 실제 실행은 요청을 보낸 쪽(이 앱)이 한다. OpenAI 호환 API의 구조가 그렇다.
- **도구 호출의 주의점:** gemma-4는 함수 호출을 지원하고, llama.cpp 서버는 `--jinja`로 도구 호출을 받는다. 그러나 확인된 주의점이 있다.
  - gemma-4는 추론 흔적을 강제로 내보내서, 도구 호출이 `reasoning_content`로 새는 문제가 보고됐다(`enable_thinking:false`로 우회).
  - 일부 GGUF는 llama.cpp가 도구 호출 형식을 인식하지 못한다.
  - 4B 모델의 도구 선택은 흔들린다.
- **결정적 파이프라인:** 무엇을 조회할지는 앱이 분류별 규칙으로 정하고, 모델은 분류·뜻 분해·판정만 한다. 요청 수가 예측되고, 작은 모델에서도 안정적이며, 단위 테스트가 쉽다.
- **결론:** 결정적 파이프라인으로 만든다. 도구 호출 모드는 큰 모델을 쓰는 사용자용으로 나중에 검토한다.

## 6. 근거 출처(조사 결과)

### Tier 0: 앱과 로컬 모델만으로(별도 서버·계정 없음)
- **가타카나→한글 표기법 변환기:** 국립국어원 일본어 표기법과 외래어 표기법 규칙을 순수 함수로 구현한다. 일본어 이름의 기준선이다. 가타카나만으로는 판타지 이름의 원어를 알 수 없어(カミラ: 가미라·카밀라 모두 가능) 표기를 대신 정하지 않고, 크게 어긋난 표기를 표시하는 검사로만 쓴다.
- **원문 안의 근거:** 작가가 단 루비가 가장 강한 읽기 근거다. 같은 이름이 여러 회차에 나온 문맥을 모아 모델의 분류·판정에 넣는다. 작품 소개·키워드는 앱이 이미 접속하는 소설 사이트에서 얻는다.
- **로컬 모델 다단계 추론:** 분류 → (별명이면) 구성 글자·단어의 뜻 분해 → 문맥상 가리키는 대상 → 표기 조합 → 3회 판정 다수결. 실험의 '미노의 마무'처럼 뜻을 몰라서 생긴 오류를 줄이는 게 목적이다.
- **(검토) 한자 뜻 사전 KANJIDIC2(EDRDG):** 한자마다 영어 뜻과 한국어 음이 들어 있다. 별명의 뜻 분해(蝮→viper)를 오프라인으로 돕는다. 크기와 라이선스(CC BY-SA 계열)를 확인한 뒤, 필요한 필드만 추려 넣을지 정한다.
- **(제외) JMnedict(일본어 인명 사전):** 약 74만 항목·146MB(변환본 기준)라 APK에 넣기 어렵다.

### Tier 1(선택): 키 없는 공개 사전 API, 앱이 직접 조회
- 별도 서버 없이 앱이 소설 사이트에 접속하듯 직접 묻는다. 사용자가 켤 때만 쓴다.
- **위키데이터:** `wbsearchentities`(일본어로 검색) → `wbgetentities`(ko 라벨, `kowiki` 사이트링크, 가나 이름 P1814).
- **위키백과(ja→ko):** MediaWiki API `action=query&prop=langlinks&lllang=ko&redirects=1`. 넘겨주기를 따라가면 별명이 실제 인물 문서로 이어진다(美濃の蝮→斎藤道三).
- Wikimedia API는 연락처가 들어간 User-Agent를 요구하고, 요청 간격을 지켜야 한다.
- 위키백과·위키데이터의 한계: 실존 인물·지명·역사 용어에 강하다. 웹소설 고유 이름과 정식 한국어판 표기는 거의 없다.
- **나무위키(3판에서 추가):** 공식 API는 없지만 별도 서버 없이 앱이 직접 조회할 수 있다.
  - **정책(2026-10-10 확인):**
    - robots.txt는 기본 전체 금지이지만 `/w/`(문서)와 `/Search`(검색)를 명시적으로 허용한다.
    - 이용약관(namu.wiki/Policy)에 자동 접근·크롤링 금지 조항은 없다.
    - 콘텐츠는 CC BY-NC-SA 2.0 KR이다.
  - **동작 확인:**
    - 자바스크립트 없는 GET만으로 검색 결과와 문서 본문이 HTML에 들어 있다.
    - 일본어 검색(`/Search?q=斎藤道三`)이 '사이토 도산 (斎藤道三)'처럼 **'한국어 표기 (日本語)' 형식**의 결과를 준다.
    - 인기 작품의 등장인물 문서도 같은 형식이 많아서, 웹소설·라노벨·애니 캐릭터명과 정식 한국어판 표기를 채울 수 있다.
  - **사용 조건**
    - 사용자가 정밀스캔을 실행할 때만 조회한다. `/Search`와 `/w/`만 쓴다.
    - 요청 간격 2~3초, 용어별 캐시. reCAPTCHA·hCaptcha 보호가 있으므로 대량 요청을 하지 않는다.
    - 태그를 걷어 낸 텍스트에서 '한국어 (日本語)' 패턴이 든 짧은 문장만 뽑는다. 난독화된 클래스 이름에 의존하지 않는다.
    - 결과 화면에 문서 링크와 CC BY-NC-SA 2.0 KR 출처 표시를 붙인다. 가져오는 것은 용어 표기 몇 글자다.
  - **위험:** HTML 구조 변경, 봇 보호 강화, 국내 접속 차단 가능성. 실패하면 다른 근거로 판정을 계속한다.

### 범위에서 뺀 것(조사 기록)
일반 웹 검색은 별도 검색 서버(SearXNG)나 외부 업체 계정(키)이 필요해서 앱 컨셉과 맞지 않아 뺐다. 조사한 선택지는 기록으로 남긴다.

| 선택지 | 조건(2026 조사) | 빠진 이유 |
|---|---|---|
| SearXNG(자체 호스팅) | 무료, `/search?format=json` | 별도 서버 운영 필요 |
| Brave Search API | 무료 등급 폐지, 매월 5달러 크레딧 | 외부 계정·키 필요 |
| Tavily / Serper | 소량 무료, 이후 유료 | 외부 계정·키 필요 |
| Google Custom Search JSON API | 신규 가입 막힘, 2027-01-01 종료 | 사용 불가 |
| Bing Search API | 2025년 종료 | 사용 불가 |

- 그래서 정식 한국어판 표기는 자동으로 찾지 못한다. 정식 번역이 없는 작품은 원래 정답이 없으므로, 일관성과 표기 규칙을 기준으로 삼고 나머지는 사람이 고친다.

### 조회하지 않는 곳
- **픽시브 백과사전:** robots.txt가 GPTBot·ClaudeBot 등 AI 크롤러를 전체 차단한다. 이 의사를 존중한다.
- **니코니코 대백과:** 자동 접근에 403.
- **소설가가 되자 API:** 작품 메타데이터만 준다. 작품 소개·키워드는 이미 접속하는 작품 페이지에서 얻는다.

## 7. 네트워크와 보안

- **현재 구조:** 웹 화면은 CSP `connect-src 'none'`이다. 외부 요청은 네이티브 HTTP 계층의 정해진 통로로만 나간다. 원문(syosetu), 사용자 모델 서버, Gemini 고정 주소가 그 통로다.
- **Tier 0만 쓰면 새 통로가 필요 없다.** 모델 요청은 기존 모델 서버 통로, 작품 소개·키워드는 기존 원문 통로를 쓴다.
- **Tier 1을 켜면** `lookup` 요청 종류를 새로 둔다. Gemini처럼 주소를 정확히 검사한다.
  - 고정 허용: `https://ja.wikipedia.org/w/api.php`, `https://ko.wikipedia.org/w/api.php`, `https://www.wikidata.org/w/api.php`, `https://namu.wiki/Search?q=…`, `https://namu.wiki/w/…`
  - 밖으로 나가는 건 용어 문자열뿐이다. 회차 본문은 보내지 않는다. 처음 켤 때 무엇이 어디로 가는지 안내한다.
  - 원문 요청처럼 간격을 둔다. 같은 용어의 조회 결과는 작품별로 캐시한다.
  - 조회가 실패하면 Tier 0 결과로 판정을 계속하고, 부분 결과임을 결과 화면에 표시한다.

## 8. Skill 검토

- **Agent Skills(SKILL.md) 표준:** Anthropic에서 시작해 agentskills.io로 공개된 형식이다. 폴더 안에 이름·설명 머리말이 붙은 SKILL.md와 선택적으로 스크립트·참고 자료를 둔다. 에이전트는 이름과 설명만 미리 읽고, 필요할 때 본문을 불러온다(점진적 공개). 형식 자체는 모델에 매이지 않는다. 다만 이걸 읽고 실행하는 건 에이전트 하네스(Claude Code, Codex, AG2 등)다. llama.cpp 서버나 이 앱의 번역 경로는 Skill을 스스로 불러오지 않는다.
- **이 앱에 붙이는 방법은 두 가지다.**
  1. **앱 안 'Skill형 지침 모듈'**
     - 정밀스캔의 분류별 지침을 '이름, 언제 쓰는가, 본문' 구조의 모듈로 둔다. 예: 일본사 인물·별명, 가타카나 표기법, 판타지 고유명사, 정식 한국어판 확인.
     - 분류 결과에 맞는 모듈만 판정 프롬프트에 넣는다. 4B 모델의 짧은 맥락에서도 지침이 묻히지 않는다.
     - SKILL.md 표준을 그대로 읽을 필요는 없지만, 같은 구조를 쓰면 나중에 2번과 공유할 수 있다.
  2. **PC 쪽 에이전트 Skill**(Claude Code·Codex용 `narou-term-scan`)
     - 사용자 PC의 에이전트가 강한 모델과 실제 웹 검색으로 정밀스캔을 하고, 결과를 앱이 가져올 수 있는 용어집 JSON으로 만든다.
     - 앱 밖의 도구라 '앱 + 로컬 LLM' 컨셉과는 별개다. 앱에는 용어집 가져오기·내보내기만 있으면 된다(#147과 연결).
- **권장:** 1번을 정밀스캔 구현의 일부로 넣는다. 2번은 컨셉 밖이므로 하지 않는다. 다만 용어집 가져오기·내보내기는 #147에서 따로 다룬다.

## 9. 단계와 결정 사항

**결정(2026-10-10, 사용자)**
1. 기능 A(번역 전 용어집 자동 생성)의 기본값은 **켬**이다.
2. 외부 조회는 **출처별로 따로 켜고 끈다**: 위키백과·위키데이터, 나무위키. 기본값은 끔이다. 처음 켤 때 무엇이 어디로 가는지 안내한다.
3. **KANJIDIC2를 앱에 내장한다.** CC BY-SA 4.0, 상업 이용 제한 없음. 출처 표기는 문서와 앱 안 라이선스 화면에 한다(시작 화면 한 줄로는 부족하다는 EDRDG 조건). 빌드할 때 한자·한국어 한자음·영어 뜻만 추려, 정밀스캔·자동 용어집이 쓸 때만 불러오는 별도 파일로 둔다. 쓰임은 별명의 뜻 풀이와 한자어 용어의 한국어 한자음 기준(王都→왕도, 魔石→마석)이다.

**단계**
1. 기반: 용어 데이터 모델(`'model'`, `'scan'`, 근거) · KANJIDIC2 내장(라이선스 화면 포함)
2. 기능 A: 번역 전 용어집 자동 생성(설정 스위치, 기본 켬)
3. 정밀스캔: 가타카나→한글 표기법 변환 검사(표시만) · 수집·분류·뜻 분해·다수결 판정(Tier 0) · 결과 화면 · Skill형 지침 모듈 · 회차 통째 재번역 경로
4. 외부 조회: `lookup` 통로 · 출처별 스위치(위키백과·위키데이터, 나무위키)

## 10. 함께 처리할 관련 결함(실험 중 발견)
- 미리 번역 화면이 모델을 서버 파일 경로로 표시한다(#180의 누락).
- 리더에 저장된 회차를 통째로 다시 번역하는 메뉴가 없다. 정밀스캔으로 용어집이 바뀐 뒤 다시 번역할 경로가 필요하다.
